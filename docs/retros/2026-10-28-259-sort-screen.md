# Retro: #259, the Sort screen (GET /api/v1/categorise/groups, POST /groups/apply, client/screens/Sort/)

## Retro summary (for the PR body)

#259 built the Sort screen: uncategorised transactions grouped by merchant, one card per merchant, quick category buttons plus More..., and Skip. Nothing wrong reached main and the review seats found real things (below). The cost was not in the build. It was about three days parked on one open decision, and the merge that the park made expensive: main moved about 130 commits, so the branch needed six conflict resolutions and three adaptations.

Gear 3 as stamped; no shift. PR #317, branch `feature/259-sort-screen`. Seats run: researcher, architect (plan posted as the PR's first comment), implementer (opus), reviewer, security-auditor (nothing new), brand-checker, test-guard, docs-syncer, and a second reviewer pass on the merge resolution. `schema-reviewer` does not apply (no migration).

Verify passed on the final tree: `npx tsc --noEmit` clean, `npm run lint` clean, `npx vitest run` 151 files / 5912 tests passed. This retro states no telemetry; the narratives are posted after `baseline finish`.

## What was built

- **Kind of code:** two endpoints (`server/db/categorise.ts`, `server/routes/categorise.ts`), the Sort screen (`client/screens/Sort/`), the `Categorise` types in `shared/contracts.ts`, and prd-02 Ruling 17. 24 files, 2823 insertions, 7 deletions; tests are roughly two thirds of that.
- **Pattern:** the group is a merchant key from the existing `merchantKeyOf` (`shared/subscriptions.ts`), not a new normaliser. Apply re-derives the group inside one DB transaction and writes every row through `setUserCategory` with source `user`, so each row gets a correction. Rows changed since the page loaded are never overwritten.
- **Why this shape:** re-deriving on apply (instead of trusting the ids the client sends) is what makes "never overwrite a changed row" checkable on the server.

## What went wrong

1. **A small decision stayed open for about three days and the lane parked the whole time.** The question was how to show "total spend" on a group with refunds or income. It went to Baseline as decision `c6c20b68` (A: money-out only plus "+$X received", recommended and built; B: net). The blocking wait died twice on Baseline `ECONNRESET` and once because the decision file had been deleted (item 2). Shipped on A after Hannah's later "take the obvious option on small choices". The decision is still open in Baseline. Cost: about three days of wall clock, and item 3.
2. **A seat rsync'd a repo copy over the shared scratch directory.** That deleted the plan, the decision file, the screenshot harness and the screenshots. Everything was rebuilt in the session's own scratchpad. Cost: the rebuild. The deleted decision file in item 1 is the same event.
3. **The park made the merge expensive.** While the lane waited, main moved about 130 commits: #391 took prd-02 Ruling 16 (the Sort ruling became 17), #236 and #412 lifted the route helpers this branch had copied, and `formatDay` gained a second argument. Six conflict resolutions and three small adaptations. The second reviewer pass on the resolution found a wrong copy note saying `client/apis/sync.ts`'s call was an identical copy; fixed.
4. **Commit subjects starting with `#259` were stripped as comments** by git's default cleanup during rebase and merge. Needed `--cleanup=verbatim`. Cost: minutes. This is the second occurrence; the #44 retro (item 5) recorded the same fault.

## Root causes

- **`long-park-on-open-decision`** (items 1 and 3). The lane stopped on a fork whose two options differ by one line of copy and are both cheap to change later. The fork was real enough to raise but not big enough to block a whole gear-3 branch for days, and no rule told the lane to build the recommended option and carry on when the choice is reversible in one file. The branch then paid for the delay in merge conflicts. The Baseline `ECONNRESET` made it longer but did not cause it.
- **`shared-scratch-dir`** (item 2). One scratch directory for every seat, no per-seat subfolder, so one seat's sync wiped another's files. First occurrence in the records I read.
- **Item 4 has no cause beyond git's comment-character default plus this repo's `#N` subject convention.** Neither is a decision to blame, but the convention is permanent, so it will recur.

## What worked, keep it

- **Researcher then architect, with the plan posted as the PR's first comment.** The plan is on the PR where the second reader can find it.
- **Reusing `merchantKeyOf` instead of writing a normaliser.** One merchant key for subscriptions and Sort.
- **Reviewer added an atomicity test with a SQLite trigger** that fails the second row's write, proving the apply transaction rolls back. A fixture that can tell the guarded behaviour from the unguarded one.
- **Brand-checker found the missing rounded-button theme token** and the reviewer switched the style; the gap itself was filed as #333, not absorbed.

- **Follow-ups filed, not absorbed:** #332 (Sort has no phone tab or Overview link; fenced), #333 (rounded-button token in Settings). Surfaced but not filed: `server/routes/spending.ts` still has its own `parseScope` copy (Housekeeping, the #236 family).

## Recommended changes

1. **Encode the commit-subject rule now, because this is the second occurrence.** Add one line to `CLAUDE.md`, under "Worktrees and lanes": commit subjects start with `#N`, which git strips as a comment during rebase and merge; use `git commit --cleanup=verbatim` (or `git commit -C <sha>` while continuing a rebase) and check `git log -1` afterwards. High leverage, cheap. Artifact: `CLAUDE.md`.
2. **Bound a decision wait and say what to do after it.** In the lane's workflow instructions, a decision whose options are reversible within the fence is raised with `--max-wait-ms` set, and on timeout the lane builds the recommended option and records "built on A, decision still open" in the PR body. Do not encode yet: this is one occurrence in the records I read, and the standing "overnight decisions" rule already covers part of it. Revisit if a second gear-3 lane parks for more than a day.
3. **Give each seat its own scratch subfolder.** Do not encode yet; first occurrence. If it recurs, the fix is one line in the seat dispatch: "write only under `<scratchpad>/<seat>/`; never rsync into the scratchpad root".

## Highest-leverage next step

Do recommendation 1: add the `--cleanup=verbatim` line to `CLAUDE.md` under "Worktrees and lanes". It is the only finding with a second occurrence, it will recur in every lane, and it is one line.
