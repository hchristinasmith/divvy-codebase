## What was built

- **Kind of code:** one SQLite table-rebuild migration, a server data module (`server/db/settings.ts`) behind `GET`/`PATCH` settings routes and `GET`/`PUT` account-role routes, an additive block in `shared/contracts.ts`, and a client Settings screen (`client/screens/Settings/`) that replaces the fake Akahu toggle.
- **Pattern:** settings are a key/value table with `key` UNIQUE, where a missing row means "the default" (`SETTINGS_DEFAULTS` in the contract) and a write is an upsert on `key`. One validation rule per `SettingsResponse` field is used both to check a PATCH and to read a stored row. The migration copies the old table into `settings_next`, drops the old, renames, and de-duplicates by "latest `updated_at` wins".
- **Why this shape:** the table could not hold a row in production as it stood (see below), so the rebuild was not optional. The contested choice was where the fix lives, and Hannah ruled it on Baseline: in this lane.

## What happened

- **The researcher found two blockers the fence could not absorb.**
  1. `settings.user_id` was NOT NULL with a foreign key to `users`, and `users` is always empty in this app (one user, no login). No setting could ever be written in production, and `key` had no UNIQUE, so an upsert had nothing to key on.
  2. `shared/contracts.ts` had no types for the account-roles endpoint, so the route and the client had nothing shared to import.
- **Two Baseline decisions were raised, and Hannah picked option A on both:** f254303a (the migration lands in this lane) and 1fef4d07 (an additive contracts block). The first raise was refused with a 400 because `options[].fence` was sent as a string, not an object; the retry went through. The lane then waited about ten minutes for the answers. The architect used the wait to plan both branches, so the wait was not idle.
- **The issue text predated prd-02 Rulings 9 to 12** (payday weekday, basis points, PATCH not PUT, `credit_card` as a fourth role, personal tax owed). The contract and the PRD won over the issue body, and the build follows them.
- **A process slip, mine (the lane):** I told the architect to read a `research.md` before I had written it. The architect found no file and re-derived the findings from the code. The result was correct; the cost was a duplicated read of the same files, size not measured.
- **origin/main moved twice mid-lane:** #211 (xero routes) and #214 (lane 191's migration `20261025140000`). Both rebases were clean. The settings migration is named `20261025150000` so it sorts after the other one.
- **Forced reconciliations, not scope creep:** the new table shape made four other files wrong, and each was changed only as far as the new shape required: `migration-guards.test.ts` (the `settings` child removed from the `users` guard, with a comment saying why), `server/db/seeds/settings.js` (new shape, currency `'$'`), `barrel.test.ts` (`settings` moves from `PLACEHOLDERS` to `EXISTING`), and `client/apis/__tests__/settings.test.ts` (error text).
- **Review ran on committed work, four build commits first.** So the review fixes (e229ac5) are their own commit and the second reader sees only the response. The pipeline step 5 versus commit-table conflict named in the #39 and #19 retros did not bite here, because the build was committed before the review seats ran.
- **Review findings, all in-fence ones fixed in e229ac5:**
  - **reviewer:** no code defects. Two tests could not fail: the rowid tiebreak, and the percent float truncation.
  - **schema-reviewer:** the migration filtered NULL values before picking the latest row, so an older value could come back after a newer NULL cleared it. Undated rows were ranked as "now", so they beat dated rows. The unique index kept the temp-table name `settings_next_key_unique` for good (SQLite keeps an index name through a rename).
  - **security-auditor:** `profitCents` was accepted up to `MAX_SAFE_INTEGER`, but safe-to-spend multiplies it by up to 10000 basis points and throws unless the product is a safe integer, so one large stored value would have made every overview request throw. Capped at 900719925474 (`MAX_SAFE_INTEGER / 10000`), and personal tax owed shares the cap. Whole error objects were logged on a 500; now `err.stack`. No server-side same-site check exists on writes (filed #218, out of fence).
  - **brand-checker:** the scope tag ignored the scope colours, selects used DM Mono, the card gap, the focus border, and the retry button style were off-token.
- **test-guard** ran about 70 mutations; 6 survived: an out-of-range date, insertion order, the `setServer` save baseline, `mutation.reset` on edit, `updated_at` refresh on conflict, and a `-0.01` input. **test-writer** closed all six in 4e4e3a3.

## What went wrong

1. **The issue was cut without trying a write against the table it depends on (Missed-by: plan).** A settings issue whose route writes `settings` rows was sliced while the table refused every write. One insert into a freshly migrated database would have shown it. Cost: a researcher finding, two Baseline decisions, a ten-minute wait, two fence widenings, and a migration (a schema-reviewer pass and a migration test of 241 lines) that the fence did not budget. No wrong code reached main. This is the same shape as #67 item 2 ("the issue assumed stored sources that do not exist") and the "consumers of the thing being changed" family: the issue was sliced from the PRD, not from the repo.
2. **Four more files were forced by the change and sat outside the fence (Missed-by: plan).** The barrel test, the migration-guards test, the seed, and a client API test were each predictable from one `rg` for `settings` and `user_id`. They were reconciled without a decision because each was a mechanical consequence, but the fence still listed none of them. By the #67 retro's count this is the seventh occurrence of the family.
3. **The `baseline decide` call was refused again for `fence` shape.** `fence` must be an object; the lane sent a string. Cost: one lost round trip. This is the fifth recorded occurrence (prd01-w2, prd01-w3, #39, #155, now #46). The #39 retro said to encode on a recurrence, and prd01-w3 and #155 said to encode now. No change reached the lane's instructions, so the lane guessed the type a fifth time.
4. **Tests that could not fail, again (Missed-by: do, caught by review and test-guard).** The implementer's own tests held two that could not turn red (the reviewer's two), and six behaviours had no test at all (test-guard's survivors). Cost: one review-fix round and one gap-test commit of 119 lines. The six survivors are all behaviour the author had no reason to doubt (a baseline reset, an ordering, a refresh on conflict), which is the same "the author's list versus the reach of the code" pattern as #39 item 2.
5. **Real defects that review found and the build did not:** the NULL-before-latest-wins order in the migration, undated rows ranking as "now", the profit cap that would have made the overview throw, the whole-error logging, and five UI token misses. The cap is the one worth noting: nothing in the contract or the issue said "stored cents must stay below `MAX_SAFE_INTEGER / 10000`", because that limit lives in `shared/safe-to-spend.ts`. Only a seat that read both files could see it.
6. **The `research.md` slip (process, mine).** I referred to a file that did not exist yet. Single occurrence; the architect's re-derivation was correct, so the cost was duplicated reading only.

## Root causes

- **Plan covers the code that changes, not the code that reads, pins or constrains it (items 1, 2 and the cap in item 5).** The same family as #25, #39 and #67. Here it shows up three ways: the table's own constraints (item 1), the tests and seeds that pin the old shape (item 2), and a downstream consumer's numeric limit (item 5). The researcher caught the first and the review seats caught the rest, which is the seats doing their job, but the plan step is where a read of `settings` and of the consumers of the stored values belongs.
- **Retro recommendations have no owner and no landing check (item 3).** The `fence` shape was recommended for encoding in three earlier retros; the fifth occurrence is this one. The cause is not the schema error (the message is clear); it is that a recommendation in a retro file is not a change until someone edits `~/.claude/CLAUDE.md` or the decision template and imports it. The record does not show anyone assigned to that edit.
- **Author's list versus the reach of the code (item 4).** Same name as #39 item 2. The implementer tests what it thought of; mutation seats find the rest. Nothing new to add except that `docs/testing.md` line 83 ("break the code it covers and watch the test go red") is a one-line rule, and #39's recommendation for an exhaustive pattern is not in that file.
- **Item 5, the cap:** the limit sat in a different file from the setting, and the contract carried no range for cents. That is a gap in the contract, not in the implementer; the reviewer and security-auditor each could have found it and the security-auditor did.
- **Item 6:** a handoff written from intent, not from the file. No deeper cause.

## Recommended changes

1. **Slicing and architect step: for any issue that writes a table, insert a row into a freshly migrated database before the fence is written; and `rg` the table name, and any column the issue drops, over the repo, and put each hit in the fence or on a named owner.** Seventh occurrence of the consumers family, and the first time the missed fact was "the table refuses the write". Artifacts: `~/.claude/agents/architect.md` (the fence checklist, then `pnpm import-workflow --name current`) and a short "Adding a table, route or mount" note in `docs/testing.md` that points at `barrel.test.ts` and `migration-guards.test.ts`. High leverage.
2. **Show the `fence` shape in the decision-file template.** Fifth occurrence; encode now. Artifacts: the `baseline decide` help text or a one-option example file in the repo, and one line in the decision paragraph of `~/.claude/CLAUDE.md` ("`fence` is an object, not a string or array; put file paths in `costs` if unsure"). I cannot see the object's real shape from the record, so I do not state it. Low cost.
3. **Record cents ranges in the contract.** A cents setting must say its ceiling next to the field in `shared/contracts.ts`, taken from the consumer that multiplies it, so the route and client import the same limit. Do not encode yet; first occurrence here, and the reviewer and security-auditor caught it. If another stored amount hits a consumer limit, add the rule to `docs/testing.md` or the contracts header.
4. **Exhaustive-by-construction tests for behaviour with a state machine** (save baseline, reset on edit, ordering). Do not encode yet. #39's recommendation (the `PRAGMA table_info` pattern) addressed schema tests and is not in `docs/testing.md`; if a third UI or ordering gap appears, add both to the assertion rules there.
5. **Handoff rule: never name a file the lane has not written.** Do not encode; single occurrence and no cost beyond duplicated reading.
