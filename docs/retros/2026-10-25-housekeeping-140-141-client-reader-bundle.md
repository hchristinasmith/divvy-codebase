# Retro: #140 and #141 Housekeeping, client tests pin the shared amount reader; drop the parseXeroJson alias

Bundled lane, branch `test/140-client-reader-bundle`. Both issues gear 1 as stamped; no shift. Both implementers ran haiku (gear 1 row of the CLAUDE.md model table). Seats, in order: implementer (#140), reviewer, test-guard, implementer (#141), reviewer, test-guard. Commits: `58ec3a2` (#140), `8aa6bfd` (#141), on `9435d52`. Gate green at each commit: tsc, lint, vitest 1050 tests then 1038 (13 duplicate reader tests deleted, 1 added). Both issues are follow-ups of #135, which froze the client test files. This retro is filed as a file at the conductor's request; it is not posted as an issue comment.

## What was built

- **Kind of code:** test-only for #140 (client tests in `money.test.ts`, `invoices.test.ts`, `akahu-client.test.ts`); a small refactor for #141 (`http.ts` imports `parseExactJson` from `shared/`, the `parseXeroJson` alias and its test block deleted, headers and two comments corrected).
- **Pattern:** wiring tests. Each row is a refusal that goes red when a named client-side guard is loosened (leading-zero regex, out-of-range clamp, `typeof` guard, linear-scan regex). The reader itself is already pinned in `shared/__tests__/exact-json.test.ts`; these rows prove each client still goes through it.
- **Result:** 7 files, +129 / -105. 13 duplicate reader tests deleted, each mapped to a shared counterpart.

## What happened

- **#140 build.** Added: Xero `007.50` and `0019.99` refusals and an out-of-range row; an out-of-range `AmountDue` -> `bad_response` in invoices; Akahu `"amount":["5"]` and `"amount":true`; the linear-scan test as `it.each` including a body ending in a lone `\`. The implementer ran four mutations and each turned the intended rows red: M1 (clamp/swallow out of range) turned the money and invoices rows red; M2 (loose regex) the two leading-zero rows; M3 (remove the `typeof` guard) only `["5"]`, with the message changing to "out of range"; M4 (linear-scan) the lone-backslash row at about 6.3 to 7.6 s against the 1 s limit. The first M4 attempt exited 127: macOS has no `timeout` binary. Cost: one wasted run.
- **The issue was wrong twice.**
  - It said an out-of-range amount throws `RangeError`. It throws `TypeError` from `assertCents` in `shared/money.ts` ("parseDollars result must be an integer number of cents"). Found when the first row was run.
  - Done-when 4 ("each new row seen red under the mutation") cannot hold for `"amount":true`. `true` coerces to `"true"`, fails `EXACT_AMOUNT`, and gives the same message with or without the guard. Only an array whose text is an amount (`["5"]`) reaches the changed path. The row stays as a wording pin, with a comment saying so, and done-when 4 is met with that one named exception. The issue already carried `Missed-by: plan`.
- **#140 review.** Two fixes: the money row pinned `shared/`'s message regex, but shared's own test pins only the class, so it became `.toThrow(TypeError)`; two comments were sharpened. The reviewer also reported a wrong `money.ts` JSDoc (fixed in #141, whose fence allows comment-only edits there), and that the timing comment in `shared/__tests__/exact-json.test.ts` claims the `(?:"|$)` ending prevents a rescan of about 7 s, while no body tested shows it. The conductor re-ran that in a scratch script: 0 to 2 ms for both variants. Filed #158 (`Spawned-by: #140`, `Missed-by: review`). test-guard confirmed all of it.
- **#141 build.** `http.ts` imports `parseExactJson`; alias gone; the 8 `parseXeroJson` blocks in `json.test.ts` (13 tests) deleted, each mapped to a shared counterpart; headers updated; one comment word in `money.test.ts` changed so the `grep` for `parseXeroJson` is empty.
- **#141 review found the real gap.** With `http.ts` swapped to a float parse then `String` (`JSON.parse(text, (k, v) => typeof v === 'number' ? String(v) : v)`), all 119 Xero client tests stayed green. The shape checks never fire because every value is still a string, and the only test that said "a double cannot hold this" lived in the block just deleted. Plain `JSON.parse` was already caught (28 failures), but only through shape errors, not through any test about exactness. Fix: an invoices row, "keeps an amount a double cannot hold exact to the cent" (`85541708717991.35` -> `8554170871799135`; the float path gives `...134`), seen red under that mutation. The reviewer also fixed a stale "(see json.test.ts)" pointer and the JSDoc source of the `TypeError`. test-guard confirmed, and flagged that the money.test.ts comment and the invoices row sit in the #140 fence, outside #141's own. The commit message says so.
- **Review fixes were folded into each issue's commit**, not a separate commit, because review ran on the uncommitted diff. This departs from the "review fixes separate from the build" commit point; the second reader here saw the finished commit, not the response to their own findings.
- **Left alone:** prettier drift in `akahu-client.test.ts` predates the lane.

## Root causes

- **Issue premises are not probed at slicing** (`issue-premise-unchecked`; second occurrence after #135's "the two regexes are identical"). #140 stated the error class (`RangeError`) and that every named row can go red, and nobody ran either. One probe each, a throw in a REPL and one mutation per row, would have given the right class and shown `true` cannot go red. Seat: plan. Cost here was small (one corrected assertion, one commented exception), because the implementer caught both while building.
- **Tests pin the reader, not the wiring** (`tests-pin-reader-not-wiring`; second occurrence: #135's fence froze the client tests, now #141's deletion removed them). The deleted `json.test.ts` block was the only thing that ran the real call path (`xeroGet` -> reader) with a digit-heavy amount. Its shared counterparts test the parser alone, so "each case has a counterpart" was true and still not sufficient. The implementer's mapping step asked "is this case covered elsewhere?" and not "what else did these tests cover?". Cost: a reviewer finding, not a defect; the swap to a float parse would have shipped green otherwise.
- **Author did not mutate the new seam** (`author-blind-spot-on-own-mutants`; recurrence). The #141 implementer's checks were the grep and the gate. Nobody swapped the reader in `http.ts` until the reviewer did. This is the same author-side miss as #135 and the safe-to-spend bundle.
- **A guard test that cannot be told from a looser guard** (`guard-tests-cannot-tell-weaker-guard`) appears again, one level up: #158 is a comment in the shared test that claims a guard (`(?:"|$)` against `"`) is pinned, and it is not. Plan claim past its evidence, recorded and filed, not fixed here.
- **Environment, minor:** macOS has no `timeout`; one exit-127 run. Not a cause worth a change.

## What worked well, keep it

- **Mutation list in the issue, run by the implementer, then re-run by the reviewer on different mutations.** M1 to M4 gave a falsifiable done-when; the reviewer's own float mutant found what the list did not. Keep both: the issue's list as a floor, a reviewer mutation on every seam the diff creates.
- **Surfacing, not absorbing.** The wrong `money.ts` JSDoc waited for #141's comment-only fence; the `(?:"|$)` comment became #158 with scratch-script evidence (EXECUTED) instead of a drive-by edit in `shared/`.
- **Naming the one row that cannot go red.** The `"amount":true` comment and the stated exception in the commit keep done-when 4 honest rather than quietly satisfied.
- **Stating the fence widening in the commit** (reviewer-driven, test-guard flagged), instead of leaving it for the conductor to find.
- **Deleting duplicates with a per-case mapping to the shared counterpart.** The mapping is what made the reviewer's gap findable: the one case with no wiring counterpart was visible.

## Recommended changes

1. **Issue slicing: probe before writing done-when. Second occurrence, so encode (high leverage).** For a follow-up that names an error class, a message, or "each row red under a mutation", the issue writer runs one throw per class and one mutation per row, and marks any row that cannot go red as a "wording pin". Artifact: the issue template used by the slicing seat (path not in this repo; the conductor owns it). The text to add: "Done-when that names an error class or a red-under-mutation row carries the command that showed it."
2. **Test deletion: add "what else did these tests cover?" to the step. Second occurrence, so encode (high leverage).** Any issue that deletes a duplicate test block must list, for each deleted test, the shared counterpart and the call path the original ran that the counterpart does not (`xeroGet` -> reader, not reader alone), and keep or add a row there. Artifact: `docs/testing.md` (a short "deleting tests" section) and the `implementer` agent's checklist, `~/.claude/agents/implementer.md`, imported with `pnpm import-workflow --name current`.
3. **Refactor lanes: reviewer swaps the changed seam.** The reviewer's float-parse swap found the gap; make it explicit for "repoint a caller" diffs: swap the callee for the nearest wrong implementation and require a red test. Artifact: `~/.claude/agents/reviewer.md`. First occurrence in this exact form; optional until it recurs (it overlaps `author-blind-spot-on-own-mutants`, which is already on its third occurrence).
4. **Mutation timing on macOS.** Use `perl -e 'alarm N; exec @ARGV'` or vitest's own timeout, not `timeout`. First occurrence, optional; not worth a file.
5. **Open:** #158 (the unproven `(?:"|$)` comment). I did not check whether the boundary-input and next-looser-guard recommendations from earlier retros landed.

## Highest-leverage next step

Add change 2 to `docs/testing.md` and the `implementer` agent: a test-deletion step that names the call path each deleted test exercised and keeps one row that still runs it. It is the only item here where a green gate hid a regression-shaped hole until a reviewer found it.
