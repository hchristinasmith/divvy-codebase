# Retro: #264 prd02, Hannah's drawings are derived at read and left out of spending, budgets and subscriptions

## Retro summary (for the PR body)

#264 makes a transfer out of a `strawb` account, matched by the same amount arriving in a `personal` account within a few days, a drawing (prd-02 Ruling 15). It is worked out on every read by a pure matcher in `shared/drawings.ts` and never stored. Both halves come back with category `Drawings` and source `rule`, and Hannah's own category on a row wins. A row whose effective category is Drawings is left out of safe-to-spend spending, budget actuals and subscription detection; balances still move. There is no migration and no fenced file is touched. The final gate is green on 3e7ed4d (tsc 0, lint 0, vitest 93 files / 3473 tests). Review found that one odd row could 500 both transaction lists, and test-guard found 13 surviving mutants the implementer's own mutation pass had missed; both were closed with small commits. The costs worth fixing are that the implementer's mutation pass keeps stopping short of what test-guard finds, and that `npm run lint` does not run prettier.

Gear 4 as stamped, no shift. Implementer on opus (the CLAUDE.md table, gear 4). This file states no telemetry (model, duration, tokens, tool calls); the lane posts the four narratives after `baseline finish`.

Seats, in order: researcher, architect, implementer (regression tests), implementer (build), reviewer and security-auditor, implementer (review fixes), docs-syncer, test-guard, implementer (test gaps), implementer (one more test for the overview error mapping), this retro. Four implementer dispatches in all. Every seat the gear 4 table lists ran. The brand-checker does not apply (no UI). The second-opinion seat (OpenRouter) was tried and failed with an invalid key; it produced nothing, and I did not substitute for it. Verify passed on the final state: on 3e7ed4d the gate ran immediately before the commit, after `prettier --write`, with the tree unchanged since. test-guard's "covered and gated" verdict was given on ebb1e7a; the four commits after it are docs, tests and formatting, each gated green.

Commits (`git log --oneline 2c2eea7..HEAD`): 0fbdaaa (regression tests), 5b4b0c1 (build), ebb1e7a (review fixes), ef72fde (docs sync), e93cdba and 0f4bd6b (test-guard gaps), 3e7ed4d (prettier). The diff is 25 files, +2847 / -38. About 2300 of those lines are tests; production code is `shared/drawings.ts` (225), `server/db/drawings.ts` (111) and small edits to the read paths.

## What was built

- **Kind of code:** a pure matcher (`shared/drawings.ts`), a db loader that finds candidate rows and lays the result over each one (`server/db/drawings.ts`), and edits to the read paths: the two transaction lists, accounts, the overview, subscriptions and `shared/safe-to-spend.ts`. A new selectable category list in `server/db/categories.ts` (the 'Divvy' group) holds Drawings. No migration, no new table, no fenced file.
- **Pattern:** derived at read, the same shape as the overview and subscriptions. Window is -1..+3 NZ calendar days, exact amount, `strawb` out and `personal` in, greedy one-to-one pairing that does not depend on input order. The effective category is computed per row and everything that sums money asks it.
- **Why this shape:** the architect weighed writing the category with a rule against deriving it, and derived won. The one category writer, `setUserCategory`, is fenced and writes corrections that feed the prd-04 learner, so a rule write would teach the learner that Hannah categorised these rows. A stored value would also go stale: the partner half can land days later, pending rows are re-inserted on every sync, and scope is editable (#260). Drawings sit in a separate list from the agent categories so the fenced agents contract test stayed green and the agents cannot propose Drawings.

## What happened

- **Researcher, then architect.** The architect made the derive-at-read call above and accepted an import cycle between `server/db/overview.ts` and `server/db/drawings.ts`.
- **Regression tests first (0fbdaaa).** Spending, budgets and subscriptions were pinned green on the old code, and mutation-checked so they fail when the behaviour moves. This is the pipeline's step 2 done as written, and it is why the build commit could show exactly which assertions changed (a few lines in `transactions.test.ts`).
- **Build (5b4b0c1).** 21 files; the implementer ran 19 mutations and all were killed. That number turned out to be the wrong comfort (below).
- **Review (ebb1e7a).** security-auditor found W2: one odd row, for example a date in year 275760, made the matcher throw, and that 500'd both `GET /transactions` and `GET /accounts/transactions`. Before #264 those lists did not depend on the cleanliness of any row's date, so the feature had added a new way for them to fail. W3: the matcher's error message carried ids and amounts, and the route logged it. Fixes: `loadDrawingIds` skips a candidate whose NZ date is not `YYYY-MM-DD` or whose amount is not a safe integer, and the route logs only the error class. Both fixes came with tests.
- **Docs sync (ef72fde).** Four stale comments or doc lines (category list comments, the PATCH rule now naming Drawings) and a pointer from Ruling 14 to Ruling 15.
- **test-guard.** Ran 35 extra mutations; 13 survived, and 4 of those were equivalent mutants (no observable difference). The real survivors were: the null-date filter, the subscriptions and overview error-mapping catches, and the calendar-date guards. e93cdba and 0f4bd6b closed them with tests only.
- **A mock that could not reach.** The first overview error-mapping test used `vi.mock` on `server/db/drawings.ts`, which does not reach `overview.ts` because of the import cycle the architect accepted. The spy moved to `shared/drawings.ts`, which both sides import.
- **A date row that did not catch its bug.** The brief named a `0050` row to catch the `Date.UTC` bug in the calendar guard. It did not. A pair `0099-12-31` to `0100-01-01` did.
- **Prettier (3e7ed4d).** `npm run lint` is `eslint --ext ...` with no prettier step, so two test files that the branch had left unformatted passed the gate at every earlier commit. They were found only by running prettier by hand.

## What went wrong

1. **13 mutants survived the implementer's pass (Missed-by: do; the reviewer and security-auditor did not look for them either).** The implementer killed 19 of 19 mutations of its own list. test-guard then ran 35 more and 13 survived, of which 9 were not equivalent and had to be closed with tests. The surviving ones were all in the new code's failure and guard branches: the null-date filter, the two catch-and-map handlers, the calendar guards. The happy path was well covered. Cost: two commits (e93cdba, 0f4bd6b), one extra implementer dispatch (the fourth, for the overview error-mapping test alone), and a test-guard round that the build was supposed to leave nothing for. No wrong code reached main.
2. **A new feature made two existing lists depend on row cleanliness (Missed-by: plan, caught by review).** `GET /transactions` and `GET /accounts/transactions` worked on any row before. Once they ran the matcher over candidate rows, one row with a year-275760 date threw and took the whole response down with it. Nothing in the plan's failure list covered "a row the matcher cannot parse". security-auditor ran it and reproduced the 500. Cost: one review-fix round (ebb1e7a). On main this would have shown as Hannah's transaction list going blank, with no hint which row was to blame.
3. **The matcher's error message carried ids and amounts and was logged (Missed-by: do, caught by review).** The project rule is to log the error class (the same rule #229 followed). The matcher's own message bypassed it. Small, but it is money data in a log line.
4. **The `vi.mock` that could not work (Missed-by: plan).** The architect accepted the `overview` and `drawings` import cycle without noting what it does to mocking. The implementer wrote a test that could never fail and found out only when it did not catch a mutation. Cost: one rewritten test.
5. **The brief's date row did not catch the bug it named (Missed-by: plan).** `0050` was the brief's pick of a "small year" for the `Date.UTC` guard, and it was not run against the unguarded code before the brief went out. The implementer found the working pair by trying it. Cost: a few minutes, but a wrong example in a brief that is supposed to be the known-good input.
6. **Two files passed the gate unformatted (Missed-by: verify).** The gate is three commands and none of them runs prettier. The files were reformatted by hand in a separate commit (3e7ed4d, 51 insertions and 28 deletions across two files), which also re-touched the overview test. This is not the first time prettier drift has been noticed and left (#140/#141 left drift in `akahu-client.test.ts` alone, and #102 was filed for prettier on fixtures), but it is the first time the branch added it itself.
7. **A false "no files" from my own prettier check (process).** A zsh word-split on an unquoted variable made the check list nothing, which read as "formatted". I ran the check again with an explicit list and found the two files. Cost: a few minutes and one wrong belief. Cause: a shell habit; nothing deeper I can point at.
8. **The second-opinion seat failed on an invalid OpenRouter key (tool).** It returned an error and no review. I did not look for what the key setting was. The review of record is the reviewer and security-auditor, both of which ran.

## Root causes

- **The author's list versus the reach of the code (items 1 and 5).** Same name as #229 item 3, #46 item 4 and #39 item 2. The implementer mutated the cases it had thought of when it wrote the code, which are the cases it tested. The mutants that survived were exactly the branches that handle input the implementer did not picture: a null date, a thrown error, a date at the calendar's edge. That is the same family as #229's survivors, in a new place. This is the point where an in-lane habit stops being enough, because the family has now recurred across a dozen retros; `docs/testing.md` still has no list of the branch kinds a mutation pass must cover.
- **A new dependency in an old read path (item 2).** The plan treated "add drawings to the list" as adding a field. It was also adding a way for the list to fail. Name it **new failure mode on an old path**. The cure is a plan-time question, not a review-time one: for every existing endpoint the feature now calls into, what can that call throw on a row that was fine before?
- **A gate that does not check what the diff touches (item 6).** The rule in CLAUDE.md is to run three commands. The commands do not include the formatter, so a green gate says nothing about formatting. The implementer ran them as required; the gate was the thing that was wrong.
- **An accepted cycle with a price nobody wrote down (item 4).** The architect accepted the import cycle as the lesser cost, which was reasonable. The price (a module mock cannot cross it) was not recorded, so the implementer paid it by finding out.
- **Items 3, 7 and 8:** item 3 is a missed rule (log the class), nothing deeper; item 7 a shell habit; item 8 a bad key. No further root cause I can point at.

## What worked, keep it

- **Regression tests green on old code, mutation-checked, committed first (0fbdaaa).** The build commit's diff to existing assertions is small and visible, which is how a reader can see that behaviour outside drawings did not move.
- **Derive at read, with the reasons written down.** Because the architect named the learner feed, staleness, pending re-inserts and editable scope, no one re-opened the question during review. The result is no migration and no fenced file, and a design that cannot go stale.
- **The user's category wins.** One rule, tested, and the same line that protects the prd-04 learner.
- **Security-auditor ran on a route change and found W2, which review and tests had not.** A feature whose own tests were green had a new 500 on an existing list. That seat earned its place.
- **Separate commits for review fixes, docs, test gaps and formatting.** The second reader saw only the response each time.
- **Counting equivalent mutants.** test-guard separated 4 equivalent survivors from 9 real ones, so no one wrote tests for nothing.
- **Putting the spy on the shared module.** Moving it to `shared/drawings.ts` made the test work without touching the cycle.

## Recommended changes

1. **Put the branch kinds a mutation pass must cover into `docs/testing.md`.** After the one-line rule, add a short list: every null or NaN filter on a loaded row, every `catch` that maps an error to a status, every calendar or range guard (test with the value just inside and just outside, and a year below 100 and above 9999), every write path that takes a scope. Name each as a mutation to run ("remove the filter", "change the status in the catch"). Why: the survivors were all of these kinds, and they recur across retros. Leverage: high. File: `docs/testing.md`. This is past the first occurrence, so it should be encoded now.
2. **Add prettier to the gate.** Either add `"format:check": "prettier --check ."` to `package.json` and list it in the CLAUDE.md pre-commit block, or run `prettier --check` on the changed files in the gate script. Why: a gate that passes unformatted files is not the gate CLAUDE.md says it is, and it cost a commit and a re-touch of a 291-line test file. Leverage: high, and cheap. Files: `package.json` and `CLAUDE.md` (the "Pre-commit checks" block). Note `.prettierignore` exists, so check what it excludes first (#102/#103 filed a fixture problem with prettier rewriting number literals).
3. **Add a plan-time question for endpoints a feature newly calls into.** In the architect's checklist: "for each existing endpoint that now calls the new code, what does a bad row do?" Why: W2 was only found by the security-auditor. Leverage: medium. File: `~/.claude/agents/architect.md`, imported with `pnpm import-workflow --name current`. First recorded occurrence under this name, so hold it; if a second feature widens an old path and review finds a new 500, encode it then.
4. **When the architect accepts an import cycle, write the mocking consequence next to it.** One line in the plan: "mock at `shared/`, not at the db module". Why: item 4. Leverage: optional. First occurrence, so do not encode yet.
5. **Run an example in the brief against the unguarded code before sending it.** Do not encode; single occurrence, and the implementer's own try-and-see fixed it in minutes.

## Highest-leverage next step

Do Recommendation 1: add the "branch kinds a mutation pass must cover" list to the assertion rules in `docs/testing.md`, and have the implementer's mutation pass work through it. The same family of survivors (a case the author did not picture, found by test-guard) has now come up in a dozen retros, and each lane has paid for it again with a gap-test commit and an extra dispatch.
