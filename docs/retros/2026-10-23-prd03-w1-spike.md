## What was built

- **Kind of code:** a throwaway spike, not advisor code. `mcp/spike/hello.ts` is a stdio MCP server (SDK `McpServer`) with one read-only `hello` tool. `mcp/spike/__tests__/hello.test.ts` spawns it. `mcp/spike/RUNBOOK.md` is the procedure Hannah runs on her real machine to learn whether Claude desktop reaches the server over Tailscale SSH (path A) or `fly ssh console` through `su` (path B).
- **Shape:** nothing imports the spike, it exports nothing, the registry does not serve `hello`, and a test pins both. It is meant to be deleted once the spike is recorded.
- **Bundle:** esbuild to a single file with no `--packages=external`, so it runs on a machine with no `node_modules`.
- **Why `McpServer` here and the low-level `Server` in #68:** the spike needs no per-call audit, so the high-level class is the shortest path to a working stdio server.

## What went wrong

1. **The architect stated a falsehood about the SDK as fact.** The plan said the SDK `Client` validates every line, so a stray stdout line would fail test (a). The implementer tried it: a stdout banner left (a) green. The SDK client sends an unparseable line to `onerror` and drops it. Test (a) was fixed to collect `client.onerror` and assert it saw nothing. Cost: small, because the implementer tested the claim before relying on it. Had the plan been trusted, the test guarding the one rule that matters here (stdout is the protocol stream) would have passed while guarding nothing.
2. **Three runbook bugs, all found by the reviewer, none by the author or gate** (fixed in 04f2b37):
   - `command -v useradd su node tailscale` under dash reports only the first name. EXECUTED. The preflight would never have listed `tailscale`, so path A would have been wrongly recorded untestable. This is the worst of the three: a wrong spike result, not a visible error.
   - `ps -ef` does not exist in `node:22-bookworm-slim`. EXECUTED. Replaced with a `/proc/*/cmdline` loop.
   - Cleanup order. `userdel -r divvy-mcp` refuses while Claude desktop holds a spike session, so the config entries must go first. REASONED, not executed.
3. **Conductor commit carried a `Co-Authored-By: Claude` trailer.** It came from the harness attribution reminder and contradicts `~/.claude/CLAUDE.md` ("never Claude as co-author"). Caught and amended before the push; no cost beyond the amend. It is a live conflict between two instruction sources, and the harness reminder is injected on every session.
4. **Smaller catches, fixed at plan or build time and not a miss:** no top-level await (tsconfig `module` is ES2020, error TS1378), so `main()` wraps it. Dropping `--packages=external` from the bundle was needed or it dies `ERR_MODULE_NOT_FOUND` on a machine without `node_modules` (EXECUTED).

## Root causes

- **Runbook commands were written for the author's shell, not the target's (2).** The author works in zsh/bash on a full userland; the target is dash in a slim image. Bugs one and two are the same cause. The gate cannot see it because the runbook is prose; only the reviewer ran the commands against the real image layers. Nothing in the plan or build asked for that.
- **A claim about third-party behaviour went into the plan unexecuted (1).** The architect prototyped, but did not try the one case (a stray stdout line) the test exists to catch. Plan text read as fact. The implementer's habit of trying it is what saved the day, not any rule.
- **Ordering of a destructive step was never walked through as a user (2, third bug).** REASONED, and not executed here either: nobody ran a session against a created user and then tried the cleanup. Unclear whether that could have been tested without Hannah's machine.
- **Two sources for one rule (3).** The user's global file and the harness reminder disagree on the commit trailer, and the lane brief did not say which wins.
