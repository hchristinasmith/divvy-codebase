## What was built

- **Kind of code:** a storage-and-refresh module, `server/xero/vault/`, that is the only code allowed to hold Xero credentials (prd-05 Rulings 2 and 3). `crypto.ts` encrypts fields, `store.ts` reads and writes the connection row, `refresh.ts` decides whether to hand out the stored access token or refresh, `vault.ts` wraps the two, `errors.ts` and `types.ts` carry the contract. The token exchange itself is injected, so the vault never calls Xero.
- **Pattern:** the tokens and the tenant are AES-256-GCM under `XERO_TOKEN_KEY`, read only from `process.env`. A refresh calls the exchange once and commits the new pair in a single `UPDATE ... WHERE version = ?` before the access token is returned. A pass whose commit matches no row discards its result and re-reads. At most one pass runs at a time per `Knex` object (a `WeakMap` keyed on the object), so concurrent callers share one exchange. A failed exchange marks `needs_reconnect`, keeps the stored ciphertext and never retries.
- **Why this shape:** Xero issues a new refresh token on every exchange, so a crash between Xero's answer and the commit can lose the pair, and no ordering of "ask" and "store" closes that window. The real alternatives were a retry on failure (refused: after a network error the vault cannot tell whether Xero rotated the token) and ordering tricks (none close the window). The module therefore does not claim to close it; it guarantees that the old pair is never overwritten before the new one is committed, and that a loss is loud (`needs_reconnect`), never silent.

## What went wrong

1. **The single-flight was per instance, not per database (reviewer finding 1).** Two `createXeroVault` calls on one database each had their own in-flight promise, so they could send the same refresh token to Xero at once. With no known grace period (#40 is open), the refresher Xero refuses can mark `needs_reconnect` before the answered one commits, and both then fail. The plan and the build both described the guard as "the in-process single-flight" without asking what "in-process" keys on. Fixed in `6ba2369`: the in-flight map is a `WeakMap` keyed on the `Knex` object. A second `Knex` object on the same file, or a second process, is still a second refresher, and the header now says so.
2. **An expiry past the year 9999 could lose a rotated grant (schema-reviewer W1, EXECUTED).** `expiresInSeconds = 1e12` gives an extended-year ISO string that the `expires_at` CHECK refuses. The refusal came after Xero had already rotated the pair, so it surfaced as `storage_failed` with the new pair gone. Fixed in `6ba2369` in `store.ts`: an expiry past 9999 is refused as bad input or a bad grant, before anything is written. A schema reviewer on a lane that adds no migration was worth it: it read the CHECK constraint against the value the code can produce, which nobody else did.
3. **Four comments claimed more than the code did.** The `refresh.ts` header said the commit was "the only point at which a refresh can lose a token" (it also loses one on a lost answer and on two refreshers); the crypto header implied key rotation (there is no fallback key); the types doc contradicted `refresh.ts`; and the redundant promise wrapper around the exchange carried a comment that was wrong (the wrapper was removed). All fixed in `6ba2369`. Each was a sentence true of the case the author pictured.
4. **The crash-(b) test could not tell two failures apart (test-guard).** Its trigger fired on any version change, so it also aborted the `needs_reconnect` write. A mutant that flagged `needs_reconnect` on any commit failure survived, because the trigger blocked the flag write too. The trigger is now narrowed to the token columns, so only the token write aborts. Reviewer had run 29 real mutants, all killed, and test-guard still found this one: the mutants the author and reviewer picked were drawn from the failures they pictured. Test-guard also found the refresh skew boundary unpinned; it is pinned now (`REFRESH_SKEW_MS`, 60 000 ms, exactly at and one past).
5. **The implementer's first tests were weaker than they looked.** Its own mutation pass in a scratch copy found two: the key-not-in-`decrypt_failed`-message check looked only at the new key, and the blob length guard was untested because short blobs never authenticate (they fail on a different branch). Both were fixed before hand-back. This is a keep, not a miss, but it is the same shape as item 4 one step earlier.
6. **The conductor dispatched the reviewer before committing the build.** The build and the reviewer's edits then shared one working tree, and the project rule is that review fixes are a separate commit. Recovery: snapshot the implementer's tree, restore it, gate and commit it, then restore the reviewed tree. No `git stash`. Cost: extra conductor steps and one gate on the restored tree. Nothing shipped wrong. The #233 retro records the same reconstruction (build and review fixes in one tree, split after the fact), so this is at least the second lane with it.
7. **A never-settling exchange blocks every caller (reviewer finding 2).** The vault will not time out the exchange, and it cannot retry, so one hung call holds the single-flight for everyone. Not fixed here: a timeout belongs to #65's exchange, so it is documented in `refresh.ts` and noted on #65.

## Root causes

- **A guard is described by its mechanism, not by what it is keyed on (item 1).** "A single-flight" is correct; "per vault instance" was an implementation accident that the word hid. Any in-memory dedupe is only as wide as its key. No plan line asked what the key was and which callers share it. Symptom: two vaults could both refresh. Cause: the plan accepted the mechanism's name as the scope.
- **A value the code can produce was not checked against the constraint that stores it (item 2).** The column CHECK and the code's arithmetic lived in different files, and the failure is after an irreversible external step (Xero rotated the pair). Nothing in the plan said: for each value that is written after the exchange, can it fail the write? A refusal that comes after the exchange loses the pair, so it has to be moved before it.
- **Claims written from the case the author pictured (item 3; recurrence).** The same family as the #113 audit-ceiling retro ("a sentence that was true of the case the author pictured") and the #136 comment rewrite. Here four comments were wrong at once, and the `refresh.ts` header was the most exposed because it is the only place the design is argued. Comments are not tested, so reviewer and test-guard are the only gate.
- **Author-written tests have the author's blind spots (items 4, 5; recurrence).** The implementer caught two of its own, the reviewer's 29 mutants were all killed, and test-guard still found one that survived. Each seat's mutants came from the failures it could picture. The fix lands because a different seat tries to break the tests, not because any seat stops writing weak ones.
- **Two instructions disagree on when review happens (item 6; recurrence).** The global pipeline step 5 says to review "as soon as the diff exists, before gate and commit", and step 7 says "review fixes, separate from the build". Following step 5 literally is what leaves build and review edits in one tree. The same reconstruction appears in the #233 retro and again here. It is not a one-off slip; the two lines are a plausible cause, though I could not confirm from the record that the conductor read step 5 literally.
- **An unmeasured external behaviour (items 1, 7).** Whether Xero honours a rotated refresh token, and for how long, is recorded nowhere (#40 is open). The researcher found this, and the crash-window comment was written to claim no grace period and no figure. That is honest uncertainty, not a miss; only the spike can close it.

## What worked, keep it

- **The researcher's three facts, each of which shaped the build.** The old-refresh-token grace period (#40) is recorded nowhere, so the comment claims none and the test asserts only what the vault does, not what Xero does. Knex errors embed bound values (ciphertext) in `err.message`, so the vault must not let a database error's text reach a caller; the scrub test dumps every table and the console and checks for token text. The single-connection sqlite pool deadlocks if the base `db` is awaited inside a `trx`, so the build avoids awaiting it there.
- **Mutation testing in a scratch copy, at every seat.** The implementer found two weak tests of its own. The reviewer ran 29 real mutants, all killed. Test-guard found the one that survived. None of it touched the working tree.
- **Reviewer, security-auditor and schema-reviewer in parallel, on different questions.** Reviewer found the per-instance single-flight, schema-reviewer found the year-9999 expiry, security-auditor found that the key is not in the database, the image or the replica (it checked `Dockerfile`, `fly.toml`, `start.sh` and `litestream.yml`) and filed the rest. No seat duplicated another's finding.
- **Review fixes as their own commit.** `6ba2369` is readable apart from the build; a second reader sees only the response.
- **Cheap model for narrow test gaps.** The three test-guard gaps went to haiku; nothing in the record says they came back for re-work.
- **The fence held, and the conductor surfaced rather than absorbed.** Everything the security-auditor found outside the fence went to an issue (below), not into the diff.
