## What was built

- **Kind of code:** the sync orchestrator for prd-01 wave 2: `runSync` in `server/sync/run.ts` (claim, fetch, apply, close) and the write path in `server/sync/upsert.ts`, with three test files and a shared in-memory-SQLite harness that fakes the Akahu client.
- **Pattern:** claim-then-apply. A `sync_runs` row is claimed first (a `running` row younger than 30 minutes makes the run return `skipped`; an older one is closed as `failed` at claim time, on every run). Settled rows are selected, diffed and updated or inserted by `akahu_id`; pending rows are one `DELETE` of `status='pending' AND source='akahu'` and a re-insert, all inside one database transaction. The fetch window is `min(now - 30d, last success's start - 30d)`, with 730 days when no run has succeeded. Writes never touch the user's category columns.
- **Why that shape:** the contested choice was the window. A window counted back from now silently skips everything inside an outage longer than 30 days. Hannah picked the `min()` form, which became prd-01 Ruling 10. The code does select-diff-update, not the `ON CONFLICT DO UPDATE` that Ruling 1 names, because Done-when 1 needs the run to count inserted versus updated rows.

## PR paragraph

This adds `runSync`, the prd-01 sync orchestrator: it claims a `sync_runs` row, fetches settled and pending transactions, and applies them in one database transaction. Settled rows are upserted by `akahu_id` without touching the user's category columns, and pending rows are mirrored by one delete-and-reinsert of the Akahu pending set.
